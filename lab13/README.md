## The layers, and why there are three

```
HTTP  →  ProductController   routes, status codes, request validation
         ProductService      business logic
         ProductRepository   data access (generated by Spring)
                 ↓
              H2 database
```

Each layer talks only to the one below it. The controller never touches the
repository, so a rule added to the service applies no matter which endpoint calls it,
and swapping H2 for Postgres touches nothing above the repository.

**Dependencies are injected through constructors**, not fields. The dependency is
`final`, the object cannot exist half-built, and the class can be constructed in a
test with a plain `new` — none of which `@Autowired` on a field can promise.

### The repository has no implementation

```java
@Repository
public interface ProductRepository
        extends CrudRepository<Product, Integer>, PagingAndSortingRepository<Product, Integer> { }
```

That is the entire file. Spring Data generates a proxy at startup and registers it in
the container, and `findAll`, `findById`, `save`, `count` and the rest exist with no
SQL written.

**Extending both interfaces is deliberate.** Since Spring Data 3,
`PagingAndSortingRepository` no longer extends `CrudRepository` — they were split, so
neither alone gives CRUD *and* paging. The handout's version extends both for exactly
this reason, and `/paged` demonstrates what that buys: page size, page number and
multi-field sorting handled by Spring from query parameters.

## Money is `BigDecimal`

The handout is explicit, and it is the same point Lab 11 ran into from the other
direction:

```java
@NotNull @DecimalMin(value = "0.0", inclusive = false)
BigDecimal price
```

with `DECIMAL(10, 2)` in the schema rather than `NUMBER`. `double` cannot represent
most decimal fractions exactly — `0.1 + 0.2` really is `0.30000000000000004` — and a
price list that cannot add itself up is not a price list. A test asserts `1210.25`
survives the database and the JSON round trip exactly.

## Validation, and the question the handout asks

> *"Test your validation by sending a negative id. Which status code do you get?"*

**500 Internal Server Error** — and that is a bug, not an answer.

`@Positive` on a path variable (with `@Validated` on the controller class, without
which the annotation is silently ignored) throws `ConstraintViolationException`.
Spring has no default mapping for it, so it escapes as an unhandled exception:

```json
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/v1/products/-5"}
```

Nothing on the server went wrong. The client sent an id that cannot exist. The correct
answer is **400 Bad Request**, and the distinction is not cosmetic: `5xx` tells a
caller *"our fault, retry later"*, so a well-behaved client will keep retrying a
request that can never succeed. `4xx` tells it to fix the request and stop.

`ApiExceptionHandler` is a `@RestControllerAdvice` that maps the exception and names
the offending field:

```json
{"status":400,"error":"Bad Request","errors":{"id":"id must be positive"}}
```

| Request | Before the handler | After |
| --- | --- | --- |
| `GET /api/v1/products/-5` | 500 | **400** |
| `GET /api/v1/products/0` | 500 | **400** |
| `GET /api/v1/products/9999` | 404 | 404 |
| `GET /api/v1/products/10` | 200 | 200 |

Both answers are in the README because the handout asks what you *get*, and the honest
answer is that the default is wrong and needs fixing.

## Tests

```text
Tests run: 8, Failures: 0, Errors: 0, Skipped: 0
```

`@SpringBootTest` with `MockMvc` drives the real application — real routing, real
serialisation, real database, real validation — rather than calling the controller as
a plain object. A test that calls `controller.findById(-5)` directly would pass while
the deployed endpoint returned 500, because the validation lives in the proxy, not in
the method body.

| Test | Pins down |
| --- | --- |
| Context loads and seed data is present | 17 products from `data.sql` |
| A known product returns 200 | id, name and price all correct |
| An unknown id is 404, not an empty 200 | The mapping of `Optional.empty()` |
| **A negative id is 400 and names the field** | The handout's question, after the fix |
| Zero is also not positive | The boundary — `@Positive` excludes 0 |
| A non-numeric id is a client error | Type conversion failures stay in 4xx |
| Prices keep two decimals | `BigDecimal` survives the round trip |
| Paging and sorting work | 3 of 17, highest price first |

## Notes

**1. Spring Boot 4 renamed things the handout predates.**

| Handout / Boot 3 | Boot 4.1.2 |
| --- | --- |
| `spring-boot-starter-web` | `spring-boot-starter-webmvc` (Initializr's `web` id still resolves) |
| `org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc` | `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` |

The test import was found by searching the dependency jars rather than guessing —
the compiler error named a package that no longer exists, not the one to use instead.

**2. `@Validated` on the controller class is load-bearing.** Constraints on *method
parameters* only run when the bean is wrapped in a validation proxy. Without the
annotation `@Positive` compiles, reads correctly, and does nothing at all — a failure
mode with no error message, which is why there is a test for the negative id rather
than a glance at the code.

**3. `schema.sql` starts with `DROP TABLE IF EXISTS`.** Spring runs it on every start,
and the H2 instance can outlive a restart within the same JVM; without the drop the
second run fails on a duplicate table.

**4. The handout's `NUMBER` type became `DECIMAL(10,2)`** — the same instruction that
tells you to drop `Double` for `BigDecimal`, applied to the column.

**5. `/paged` is beyond the handout.** It asks for find-all and find-by-id; the
paging endpoint exists to show what extending `PagingAndSortingRepository` actually
gives you, since otherwise that half of the interface is invisible.
